# 배포 — 어디에 무엇을 올리고, 무엇이 언제 돈이 되는가

2026-09-16 기준. 숫자는 전부 공식 문서에서 확인한 값이다.

---

## 0. 한 장 요약

```
                    사용자 브라우저
                          │
                    ai-daeyeok.com
                          │
        ┌─────────────────┴──────────────────┐
        │  Vercel (icn1 · 서울)              │   ← Next 앱. 렌더링만 한다
        │  서버 컴포넌트 · 라우트 핸들러       │
        └─────────────────┬──────────────────┘
                          │ HTTPS
        ┌─────────────────┴──────────────────┐
        │  Supabase (ap-northeast-2 · 서울)  │   ← 백엔드 전부
        │  Auth · Postgres · Storage         │
        │  Realtime · Edge Functions         │
        └─────────────────┬──────────────────┘
                          │
                    ┌─────┴─────┐
                    │  fal.ai   │   ← Wan-Animate Replace
                    └───────────┘

Google OAuth ──→ supabase.co/auth/v1/callback ──→ 우리 도메인/auth/callback
```

**돌려야 할 서버가 없다.** Next 앱은 Vercel이 함수로 실행하고, 무거운 일(1~3분짜리 변환)은 Supabase Edge Function에서 비동기로 돈다. VM도, nginx도, certbot도, systemd도 없다.

---

## 1. 고정 IP는 필요 없다

OAuth 리다이렉트는 **IP가 아니라 URL로** 등록한다. 도메인 뒤의 IP는 매일 바뀌어도 상관없다 — DNS가 처리한다. Vercel의 IP는 실제로 수시로 바뀌지만 OAuth는 멀쩡히 돈다.

이 프로젝트는 한 겹 더 떨어져 있다. Google Cloud에 등록하는 승인된 리디렉션 URI는

```
https://<프로젝트ref>.supabase.co/auth/v1/callback
```

**Supabase 도메인이지 우리 서버가 아니다.** Next 앱을 어디에 올리든 이 값은 안 바뀐다.

고정 IP가 필요해지는 건 반대 방향뿐이다 — 상대방이 "출발지 IP를 등록하라"고 할 때(IP 제한이 걸린 DB, 일부 정산 API). 지금 구조엔 해당 사항이 없다. 생기면 그때 Supabase Edge Function 쪽에서 해결할 문제지, 웹 호스팅을 바꿀 이유가 아니다.

---

## 2. Vercel을 고른 이유

가격이 아니라 구조 때문이다.

- **백엔드가 이미 Supabase에 다 있다.** Next 앱은 서버 컴포넌트로 읽어 그리는 껍데기다. 이걸 위해 VM을 띄우고 Node·리버스 프록시·TLS 갱신·무중단 배포·OS 패치를 떠안는 건 순손해다. 솔로 개발에서 희소 자원은 서버비가 아니라 시간이다.
- **서버리스 타임아웃이 안 물린다.** 변환은 Edge Function에서 비동기로 돌고 웹은 Realtime으로 상태만 받는다. 업로드도 signed URL로 Storage에 직결된다. Vercel 함수가 하는 일은 렌더링뿐이다. (참고로 Hobby도 함수 최대 300초까지 된다.)
- **브랜치마다 프리뷰 배포**가 공짜로 생긴다. 혼자 만들 때 이게 생각보다 크다.

### Oracle Cloud를 안 쓰는 이유

2026년 6월 15일자로 Always Free ARM이 **4 OCPU/24GB → 2 OCPU/12GB로 반토막**났다. 공지도 메일도 없었고, 인스턴스가 셧다운되면서 사람들이 알아챘다. 무료라서 고른 인프라가 예고 없이 절반이 되는 쪽에 수익 나는 제품을 올리는 건 나쁜 거래다.

Oracle이 나은 경우는 상시 워커·크론·WebSocket 서버가 필요하거나 자체 GPU를 돌릴 때인데, 자체 GPU는 설계서 "쓰지 말 것"에 이미 있고 나머지도 지금 구조엔 없다.

## 3. 계정 세팅 순서

순서가 중요하다. Supabase 프로젝트 ref가 있어야 Google OAuth를 설정할 수 있고, Vercel 도메인이 있어야 Redirect URL을 등록할 수 있다.

### 3.1 Supabase

1. 프로젝트 생성. **리전은 Northeast Asia (Seoul) / `ap-northeast-2`.**
   → 나중에 못 바꾼다. 다른 리전으로 만들면 왕복 지연이 그대로 사용자 체감이 된다.
2. Project Settings → API에서 세 값을 받아둔다
   - Project URL
   - `anon` public key
   - `service_role` key — **절대 클라이언트로 나가면 안 된다. RLS를 전부 무시하는 키다.**
3. 프로젝트 ref를 메모한다 (URL의 `https://<ref>.supabase.co`)

### 3.2 Google Cloud OAuth

1. 새 프로젝트 → **OAuth 동의 화면** → 외부(External) → 앱 이름·지원 이메일 입력
2. **사용자 인증 정보** → OAuth 클라이언트 ID → 웹 애플리케이션
3. **승인된 리디렉션 URI**에 하나만 넣는다:
   ```
   https://<프로젝트ref>.supabase.co/auth/v1/callback
   ```
   우리 도메인을 여기 넣는 게 아니다. 자주 틀리는 지점이다.
4. client ID / client secret → Supabase → Authentication → Providers → Google에 붙여넣고 활성화
5. 테스트 단계에서는 동의 화면의 테스트 사용자에 본인 계정을 넣어둔다. 게시(프로덕션) 전환은 출시 직전에.

### 3.3 Vercel

1. GitHub 레포 연결 → Import
2. **함수 리전을 `icn1`(서울)로 바꾼다.** 기본값은 `iad1`(워싱턴 D.C.)이라, 그대로 두면 서울 Supabase까지 태평양을 왕복한다. 프로젝트 Settings → Functions → Region, 또는 `vercel.json`:
   ```json
   { "regions": ["icn1"] }
   ```
3. 환경변수를 §4 표대로 넣는다. **스코프를 Production / Preview / Development 전부 체크**해야 프리뷰 배포에서도 돈다.
4. 배포 → `<프로젝트>.vercel.app` 도메인 확인

### 3.4 도메인

일찍 사두는 게 낫다. Redirect URL을 한 번만 등록하고 끝낼 수 있다.

1. 도메인 구입 (가비아·Cloudflare 등)
2. Vercel → Settings → Domains에 추가 → 안내하는 A/CNAME 레코드를 DNS에 등록
3. TLS는 Vercel이 자동 발급·자동 갱신한다. certbot 같은 건 없다.

## 4. 환경변수

| 이름 | 어디에 | 클라이언트 노출 | 용도 |
|---|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Vercel · 로컬 | O | Supabase 접속 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Vercel · 로컬 | O | RLS가 걸린 공개 키. 노출돼도 된다 |
| `SUPABASE_SERVICE_ROLE_KEY` | **Supabase Edge Function 시크릿에만** | **X** | RLS를 무시한다. Vercel에 넣을 이유가 없다 |
| `FAL_KEY` | **Supabase Edge Function 시크릿에만** | **X** | Vercel에서 fal.ai를 부르지 않는다 |

**`SUPABASE_SERVICE_ROLE_KEY`를 Vercel에 넣지 마라.** 서비스 롤이 필요한 작업(크레딧 차감, job 생성)은 전부 Edge Function 안에서 일어난다. Vercel 쪽에 키가 없으면 실수로 클라이언트 번들에 섞일 경로 자체가 사라진다.

Edge Function 시크릿은 `supabase secrets set FAL_KEY=...`로 넣는다.

로컬은 `.env.local`. `.gitignore`에 들어 있는지 확인할 것.

## 5. Redirect URL — 가장 많이 걸리는 곳

등록하는 자리가 **세 군데**고, 각각 다른 값이 들어간다.

| 어디 | 무엇을 | 값 |
|---|---|---|
| Google Cloud · 승인된 리디렉션 URI | Supabase 콜백 | `https://<ref>.supabase.co/auth/v1/callback` |
| Supabase · Site URL | 기본 복귀 주소 | `https://ai-daeyeok.com` |
| Supabase · Redirect URLs | 허용 목록 | 아래 전부 |

```
http://localhost:3000/**
https://ai-daeyeok.com/**
https://ai-daeyeok.vercel.app/**
https://ai-daeyeok-*.vercel.app/**
```

마지막 줄이 핵심이다. **Vercel 프리뷰 URL은 배포마다 바뀐다**(`ai-daeyeok-git-브랜치-팀.vercel.app`). 와일드카드를 안 넣으면 프리뷰에서 로그인이 전부 막히고, 원인을 코드에서 찾게 된다.

그리고 코드 쪽:

- **`redirectTo`를 하드코딩하지 않는다.** 요청의 origin에서 뽑아야 로컬·프리뷰·운영이 한 코드로 돈다.
- 서버에서 origin을 만들 때 `VERCEL_URL`은 프로토콜이 없다. `https://`를 직접 붙이거나, 라우트 핸들러에서 `new URL(request.url).origin`을 쓴다.
- `next` 파라미터는 `/`로 시작하고 `//`로 시작하지 않는 상대 경로만 허용한다. 안 막으면 오픈 리다이렉트다.

## 6. 영상 스토리지 — 설계서와 다른 점

설계서는 `Supabase + Cloudflare R2`로 되어 있다. **MVP는 Supabase Storage 하나로 간다.** 버킷 두 벌을 관리하는 복잡도를 지금 떠안을 이유가 없다.

대신 **갈아탈 시점을 숫자로 정해둔다.**

Supabase Free는 파일 스토리지 **1GB**, egress **5GB**다. 10초 720p 클립이 대략 3~8MB이니 1GB면 **150~300개**다. 개발하면서 금방 찬다.

| 신호 | 대응 |
|---|---|
| 파일 1GB 또는 egress 5GB 근접 | Supabase Pro($25/월)로. 100GB 스토리지 · 250GB egress |
| 영상 다운로드 트래픽이 비용의 주범이 됨 | **`videos` 버킷만 R2로 이관.** R2는 egress가 무료다 |

이관이 쉬운 이유는 DB에 경로를 문자열(`result_video_path`)로만 들고 있기 때문이다. 서명 URL 만드는 함수 하나만 바꾸면 된다. 이미지(셀피·캐릭터·룩·프리셋)는 용량도 트래픽도 작으니 Supabase에 그대로 둔다.

> Supabase Free는 **7일간 활동이 없으면 프로젝트가 일시정지**된다. 개발을 잠시 쉴 계획이면 알고 있어야 한다. 활성 프로젝트는 계정당 2개까지다.

| 항목 | 지금 | 언제 돈이 되나 | 그때 얼마 |
|---|---|---|---|
| Vercel | Hobby $0 | **결제를 켜는 순간** — Hobby는 비상업용 전용이다 | Pro **$20/월** |
| Supabase | Free $0 | 파일 1GB · egress 5GB · DB 500MB 중 아무거나 초과 | Pro **$25/월** (컴퓨트 크레딧 $10 포함) |
| 도메인 | — | 지금 사는 게 낫다 | 연 1~2만원 |
| fal.ai | 종량제 | 첫 변환부터 | 설계서 원가표 참조 |
| Cloudflare R2 | — | 영상 트래픽이 커지면 | 저장 $0.015/GB, egress 무료 |

**Vercel Hobby의 비상업 조항이 제일 중요하다.** 공식 문서에 "the Hobby plan restricts users to non-commercial, personal use only"라고 박혀 있다. 웹 결제가 수익의 핵심인 제품이니, S8에서 결제를 켜기 전에 Pro로 올려야 한다.

합쳐서 **월 $45**. ₩24,900 구독 기준 **2.7명**이면 인프라가 자립한다.

## 8. 배포 순서

개발 중에는 이렇게 흐른다.

```
로컬 (localhost:3000)
  └─ git push → 브랜치
       └─ Vercel 프리뷰 자동 배포 (로그인 되는지 여기서 확인)
            └─ main 머지
                 └─ 운영 자동 배포
```

Supabase 마이그레이션은 자동이 아니다. `supabase db push`로 직접 올린다. **코드 배포보다 마이그레이션을 먼저 올린다** — 반대로 하면 새 코드가 없는 컬럼을 찾는다.

## 9. 출시 전 체크리스트

**인증**
- [ ] Google 동의 화면이 테스트 → 프로덕션으로 게시됨
- [ ] Redirect URLs에 운영 도메인이 들어 있음
- [ ] `/auth/callback?next=https://evil.com`을 직접 쳐보면 `/`로 감

**보안**
- [ ] 모든 테이블에 RLS가 켜져 있음 (Supabase 대시보드에서 경고 배지 확인)
- [ ] `SUPABASE_SERVICE_ROLE_KEY`가 Vercel 환경변수에 **없음**
- [ ] 클라이언트 번들에 `service_role`/`FAL_KEY` 문자열이 없음 — `.next` 빌드 산출물에서 검색해볼 것
- [ ] private 버킷 파일이 signed URL로만 나감

**인프라**
- [ ] 함수 리전이 `icn1`
- [ ] Supabase 리전이 `ap-northeast-2`
- [ ] 결제를 켜기 전에 Vercel Pro로 전환됨
- [ ] 커스텀 도메인 + TLS 정상

**제품**
- [ ] 크레딧 0인 계정으로 전 화면을 돌아봄
- [ ] job을 일부러 실패시켜 에러 문구가 사람 말로 나오는지 확인
- [ ] 375px에서 가로 스크롤 없음
- [ ] 신규 가입 → 첫 캐릭터까지 막히는 곳 없이 감

## 10. 사고가 나면

- **배포가 잘못됐다** → Vercel 대시보드에서 이전 배포를 Promote. 즉시 롤백된다. 이게 Vercel의 가장 큰 실질 이점이다.
- **마이그레이션이 잘못됐다** → 롤백이 어렵다. **컬럼을 지우거나 이름을 바꾸는 마이그레이션은 만들지 마라.** 추가만 한다. 컬럼을 없애야 하면 코드에서 먼저 안 쓰게 만들고, 한참 뒤에 지운다.
- **Supabase 프로젝트가 정지됐다** → Free 티어 7일 미사용. 대시보드에서 재개.
- **로그인이 갑자기 안 된다** → 십중팔구 Redirect URLs. 프리뷰 도메인이 바뀌었거나 운영 도메인 등록이 빠졌다.
